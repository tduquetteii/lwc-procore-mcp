# lwc-procore-mcp

A remote [MCP](https://modelcontextprotocol.io) server that lets an LLM assistant work with
[Procore](https://www.procore.com) construction-management data on behalf of the signed-in user.

Add it to any MCP client that supports remote servers with OAuth, sign in with your Procore
account, and the assistant can call Procore on your behalf with your permissions. The server holds
no user data: every request to `/mcp` carries the user's own Procore access token, and the server
simply forwards it to Procore.

Built with the official [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk)
(`MCPServer`, streamable HTTP transport) and can be deployed as a single container.

## How it works

Procore's OAuth 2.0 implementation does not publish discovery metadata, and its token endpoint
requires the app's client secret. MCP clients expect both to be available at the MCP server's URL.
So this server sits between the client and Procore:

| Route | What it does |
|---|---|
| `GET /.well-known/oauth-authorization-server` | Publishes the OAuth discovery document Procore does not, pointing at the two routes below. |
| `GET /authorize` | Redirects the user to Procore's login page (`login.procore.com/oauth/authorize`) with this app's client ID. |
| `POST /token` | Forwards the authorization-code and refresh-token exchanges to Procore, adding the client secret so it never leaves the server. |
| `POST /mcp` | The MCP endpoint. Every request must carry `Authorization: Bearer <procore access token>`. |
| `GET /.well-known/oauth-protected-resource/mcp` | Generated by the SDK; tells the client which authorization server protects `/mcp`. |
| `GET /health` | Returns `ok`. Used by your hosting platform for a health check. |

Bearer tokens are verified by calling Procore's `GET /rest/v1.0/me`. A token that Procore accepts is
cached in memory for five minutes so each tool call does not cost an extra round trip. Tools then
call the Procore REST API with that same token plus the `Procore-Company-Id` header, so a user only
ever sees what they could see in Procore itself.

```
Client  --(1) discovery-->  this server  (metadata, /authorize, /token)
Client  --(2) login------>  login.procore.com  (user signs in, approves app)
Client  --(3) code------->  this server /token  --(+client secret)-->  login.procore.com
Client  --(4) Bearer----->  this server /mcp    --(same token)------->  api.procore.com
```

Access tokens from Procore last 90 minutes. The client refreshes them through `/token`; Procore
rotates the refresh token on every use.

## Tools

| Tool | Arguments | Returns |
|---|---|---|
| `list_projects` | `active_only` (bool, default `true`) | `id`, `name`, `project_number`, `active`, `city`, `state_code` for each project the user can see. Use the `id` wherever another tool asks for a `project_id`. |

Every tool carries a `title` and a read-only or destructive annotation. MCP clients use these to
group tools in their permission settings and to decide which tools may run without asking first.

More tools are added by writing an `async` function decorated with `@mcp.tool()` in `main.py` and
calling `procore_get(path, params)`; see [Adding tools](#adding-tools).

## Prerequisites

- A Procore account with access to the [Developer Portal](https://developers.procore.com).
- An app in the Developer Portal with **production** OAuth credentials (Client ID and Client Secret).
- Your MCP client's OAuth callback URL registered as a redirect URI on that app. Every client
  publishes its callback URL in its documentation for remote or custom MCP servers. Procore only
  issues authorization codes to registered redirect URIs, so this step is required.
- Your Procore **company ID**. The quickest way to find it is `GET https://api.procore.com/rest/v1.0/companies`
  with any valid token, or look at the URL of a company-level tool in Procore.
- [uv](https://docs.astral.sh/uv/) and Python 3.15+ for local development.
- An MCP client that supports remote servers over streamable HTTP with OAuth and lets you supply
  your own OAuth client ID (see [Connect a client](#connect-a-client)).

## Configuration

All configuration is through environment variables. Copy `.env.example` to `.env` for local runs;
in production set them as encrypted environment variables instead.

| Variable | Required | Description |
|---|---|---|
| `PUBLIC_URL` | yes | The public HTTPS base URL of this server, no trailing slash. Used to build the OAuth metadata, so it must match the URL the client is given. |
| `PROCORE_CLIENT_ID` | yes | Client ID from the Procore Developer Portal. |
| `PROCORE_CLIENT_SECRET` | yes | Client secret from the Procore Developer Portal. Only ever used server-side. |
| `PROCORE_COMPANY_ID` | yes | Numeric Procore company ID sent as the `Procore-Company-Id` header on every API call. |

`.env` is git-ignored on purpose. Never commit it.

## Run locally

```bash
uv sync
cp .env.example .env     # then fill it in
uv run uvicorn main:app --reload --port 8000
curl http://localhost:8000/health
curl http://localhost:8000/.well-known/oauth-authorization-server
```

Hosted clients run the OAuth flow from their own servers, so to test the full flow end to end you
need a public HTTPS URL. A tunnel such as `ngrok http 8000` or `cloudflared tunnel` works; set
`PUBLIC_URL` to the tunnel URL and make sure the client's callback URL is registered on the Procore
app.

## Deploy

The server is one container with no database. Build it, run it with the four environment
variables, and put it behind TLS. Any host that runs a Docker image will do.

```bash
docker build -t procore-mcp .
docker run --rm -p 8000:8000 --env-file .env procore-mcp
```

Checklist for whichever host you use:

- Expose port 8000 (or change it in the Dockerfile) and point the health check at `/health`.
- Terminate TLS in front of the container. `PUBLIC_URL` must be the public `https://` address with
  no trailing slash, because the OAuth metadata is built from it.
- The container trusts `X-Forwarded-Proto` from the proxy (`--proxy-headers` in the Dockerfile), so
  redirects stay on `https`.
- Run a single instance. MCP sessions live in process memory, so a second replica behind a load
  balancer would not see sessions started on the first.
- Store the Procore credentials as secret environment variables, never in the image or the repo.

## Connect a client

The exact menu names vary by client, but the steps are the same everywhere:

1. Add a remote (custom) MCP server and give it the URL `https://<your-server>/mcp`.
2. Where the client asks for OAuth client credentials, enter the Procore **Client ID** as the OAuth
   client ID. Leave the client secret blank: the server injects the real secret during the token
   exchange, so the client never needs it.
3. Save and connect. The client discovers the OAuth metadata, opens the Procore login page, and
   stores the resulting token for that user.

The server does not implement dynamic client registration, so the client ID must be entered
manually. A client that only supports dynamic registration cannot connect until a registration
endpoint is added. In organisation-managed clients an admin typically adds the server once and each
member then signs in to Procore with their own account.

Try it: *"List my active Procore projects."*

## Adding tools

```python
@mcp.tool(title='List RFIs', annotations=ToolAnnotations(read_only_hint=True))
async def list_rfis(project_id: int) -> list[dict]:
    """List RFIs for a project. Use list_projects to find the project_id."""
    rfis = await procore_get(f'/rest/v1.0/projects/{project_id}/rfis')
    keep = ('id', 'number', 'subject', 'status', 'due_date')
    return [{k: r.get(k) for k in keep} for r in rfis]
```

Guidelines that keep the tools useful to the model:

- Give every tool a `title` and one annotation: `read_only_hint=True` for tools that only read,
  `destructive_hint=True` for tools that create, update, or delete. Clients group tools by these
  hints in their permission settings; a tool with neither lands in a catch-all group and is
  usually asked about on every call.
- Write the docstring for the model, not for humans. Say what the tool returns and which other tool
  supplies its inputs.
- Trim Procore's large payloads to the fields the model needs. Everything you return goes into the
  model's context.
- `procore_get` already attaches the user's token and the company header. Procore list endpoints
  are paginated (`page`, `per_page`), so add paging for endpoints that can return many rows.

## Security notes

- The server stores no tokens and no user data. The only state is a five-minute in-memory cache of
  tokens Procore has accepted, so a token revoked in Procore keeps working here for at most five
  minutes.
- The Procore client secret lives only in the server's environment. The client and the user's
  browser never see it.
- `/token` is a public endpoint that adds the client secret to whatever authorization code it is
  given. Procore's codes are single-use and expire after ten minutes, and Procore only issues them
  to redirect URIs registered on your app, so keep that list limited to the callback URLs of the
  clients you actually use.
- Procore does not support PKCE. The discovery document still advertises `S256` because MCP clients
  require it, but the `code_challenge` and `code_verifier` values are not enforced by Procore.
  Protection against code interception therefore rests on TLS, the `state` parameter, and Procore's
  redirect-URI allowlist.
- Each user acts under their own Procore permissions. Nothing in this server grants access the user
  does not already have.
- DNS-rebinding protection in the SDK is disabled because the server is only reachable over a public
  TLS hostname, where that attack does not apply.

## Troubleshooting

- **`Missing Procore-Company-Id header!`** from a tool: `PROCORE_COMPANY_ID` is unset or wrong.
- **The client keeps asking to re-authenticate right after connecting**: `PUBLIC_URL` does not match
  the URL the client was given, so the discovery document points somewhere else.
- **Procore login page shows a redirect-URI error**: the client's callback URL is not registered on
  the Procore app, or you are using sandbox credentials against production.
- **401 on every `/mcp` call**: check the server logs for the result of the `/rest/v1.0/me` check;
  a token from a different Procore environment (sandbox vs production) is rejected.
